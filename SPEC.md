## A. Чеклист применимости задачи (шаг 0)

**Проблема.** `LIMITS.md` исчерпывающе перечисляет, что пайплайн не умеет
(органика, анимация, интерьеры, ткань/жидкости), но применяется человеком
вручную и по памяти. Типовая потеря времени — начать `build.py`, и только
на середине понять, что задача в принципе не того класса.

**Решение.** Не код — документация. В `GUIDE.md`, раздел «Шаг 0. Задача»,
добавить короткий чеклист из пяти вопросов, по одному на каждую строку
таблицы «Класс задач» в `LIMITS.md`: персонаж/органика? ткань/жидкость/дым?
нужна анимация? несколько предметов, где важна компоновка друг относительно
друга? нужна чертёжная точность? «Да» на любой — сигнал остановиться до
`build.py` и решить это отдельно (impor модели, отдельный инструмент, ручная
работа), а не внутри пайплайна.

**Критерий приёмки.** Чеклист виден в `GUIDE.md` до раздела «Шаг 1», ссылки
на конкретные строки `LIMITS.md` работают.

**Выгода.** Fail-fast на уровне постановки задачи — самая дешёвая точка
отказа во всём пайплайне, дешевле даже дешёвого превью.

## B. Допуск и вердикт в сравнении силуэтов

**Проблема.** `silhouette.compare()` возвращает процент расхождения по
каждой метке, но решение «это в пределах нормы или нет» каждый раз заново
принимает человек. Без порога число нельзя использовать как автоматический
гейт (в частности — для фичи **E** ниже).

**Решение.** Добавить в `lib/silhouette.py` необязательный параметр
`tolerance` (доля, например `0.15`) в `compare()`. При наличии — рядом
с числом добавляется вердикт:

```python
def compare(reference, render, tolerance=None):
    ...
    # без tolerance — поведение не меняется, только числа
    # с tolerance — дополнительно out[label] = {"diff": -3.2, "ok": True}
```

Обратная совместимость обязательна: без `tolerance` возвращается ровно то
же, что сейчас (голое число). Порог — не предметный, живёт как параметр
вызова, а не константа библиотеки (тот же принцип, что и `fractions`).

**Критерий приёмки.** Новый smoke-чек в `tests/smoke.py`: `compare(x, x,
tolerance=0.1)` даёт вердикт `ok=True` по всем меткам; искусственно
испорченный профиль с расхождением выше порога даёт `ok=False`.

**Выгода.** Превращает измерение в решение без участия человека на каждой
итерации — необходимая база для стоп-гейта (E) и для будущей автономной
приёмки.

## C. Аудит согласованности референсов (шаг 0.5, до геометрии)

**Проблема.** Диагностированный на «Тян» случай: расхождения, приписанные
неточной лепке, частично объяснялись несогласованной дистанцией/фокусным
расстоянием между шестью экранными снимками одного объекта. Это видно по
самим референсам, ещё до того, как потрачено время на форму — но сейчас
некому и нечем это проверить автоматически.

**Решение.** Новая функция в `lib/silhouette.py`:

```python
def audit_references(paths, fractions=None, thresh=0.06, tolerance=0.15):
    """profile() каждого пути, затем медианный профиль по группе и
    отклонение каждого кадра от медианы. Возвращает {path: {...,
    "outlier": bool}} — не судит, что правильно, а что нет, только
    показывает, какой кадр выбивается из группы."""
```

Важное ограничение, которое нужно явно документировать (в духе текущего
`LIMITS.md`): эта функция сравнима только **внутри одного ракурса** —
несколько снимков, задуманных как «одна и та же поза, один и тот же анфас».
Сравнение референсов *разных* ракурсов между собой не входит сюда — это
задача фичи D.

**Место вызова.** Не в `lib/`, а как рекомендованный паттерн в
`GUIDE.md`/`template/README.md`: прогоняется на шаге 0, сразу после
получения референсов, до `build.py`.

**Критерий приёмки.** Smoke-тест: набор из трёх согласованных синтетических
силуэтов + один намеренно смасштабированный — `audit_references` помечает
только четвёртый как `outlier`.

**Выгода.** Ловит именно тот класс ошибки, который был неверно приписан
геометрии в прошлом случае — до того, как на неверную геометрию потрачено
время или деньги.

## D. Многоракурсный силуэт

**Проблема.** `silhouette.flat_render()` жёстко фиксирует анфас
(`azimuth=elevation=0`) — задокументированное ограничение: «сравнивается
только плоский силуэт анфас… согнутая фигура даёт другой профиль». Ошибки
глубины/объёма (руки прижаты в одном референсе, отставлены в другом) не
видны в одной проекции в принципе, а не по недосмотру.

**Решение.** Добавить необязательные параметры `azimuth`/`elevation`
в `flat_render()` (по умолчанию `0, 0` — обратная совместимость,
существующие вызовы не меняются):

```python
def flat_render(path, res=(700, 1150), lens=60.0, fill=1.06,
                 azimuth=0.0, elevation=0.0):
```

Использование — прогнать `profile()`+`compare()` для нескольких ракурсов
(например, front + 3/4), каждый раз с отдельным референсом того же ракурса.
Библиотека не решает, какие ракурсы значимы для конкретного предмета — это
по-прежнему решение проекта, ровно как и подписи `fractions`.

**Критерий приёмки.** Smoke-чек: `flat_render` с `azimuth=45` даёт непустой
профиль, отличный от `azimuth=0` на асимметричной тестовой геометрии.

**Выгода.** Закрывает прямо названное в `LIMITS.md` ограничение («это не
проверка 3D-формы») — не полностью, но переводит его из «нет вообще» в
«есть по нескольким проекциям», что для органических форм — основной
источник ошибок.

## E. Стоп-гейт перед платным внешним API

**Проблема.** Ничто сейчас не мешает вызвать платный внешний сервис
генерации геометрии (Meshy и подобные) на референсах любого качества.
Деньги тратятся до проверки, а не после — при том, что дешёвая проверка
(силуэт референсов) уже существует и стоит секунды.

**Решение.** Не новая функция в `lib/`, а обязательный паттерн, задокументированный
и вынесенный в `template/`: перед вызовом внешнего API проектный код обязан
вызвать `audit_references(...)` (C) и **явно проверить** отсутствие
`outlier`. Пример в `template/README.md`:

```python
audit = silhouette.audit_references(ref_paths, tolerance=0.15)
if any(v["outlier"] for v in audit.values()):
    raise RuntimeError("референсы рассогласованы — см. audit; API не вызван")
# только после этой проверки — вызов платного сервиса
```

Библиотека не может «запретить» проекту вызвать API — вызов живёт в
проектном коде, не в `lib/` (внешние сервисы, ключи, сеть — уже сейчас вне
`lib/`). Гейт — это обязательный паттерн и явная проверка, а не рантайм-замок.

**Критерий приёмки.** `template/README.md` содержит этот паттерн как
рекомендованный первый шаг перед любой интеграцией с платным API; пример
в документации проходит как часть смоук-проверки шаблона (уже покрыто
существующей стадией `check.py`, которая собирает `template/`).

**Выгода.** Прямая экономия денег на уже наблюдавшемся классе ошибки —
дешёвая проверка перед дорогим, необратимым вызовом.

## F. Сравнение с прошлым утверждённым (на каждом чекпоинте)

**Проблема.** Каждый шаг показывает только текущий вариант. Чтобы увидеть,
что изменилось после возврата на шаг 3 или 4, нужно держать прошлый кадр
в памяти — источник тихих регрессий («поправили свет, а материалы поехали»).

**Решение.** Расширить `lib/mosaic.py` функцией `side_by_side(prev_path,
curr_path, out_path, labels=("было", "стало"))`, которая просто кладёт
два PNG рядом с подписями. Использование — в `make.py` каждого проекта:
если в рабочей папке есть файл предыдущего утверждённого чекпоинта (простая
конвенция именования, например `<stage>.approved.png`), автоматически
собирать сравнение рядом с новым вариантом.

**Критерий приёмки.** Smoke-чек: `mosaic.side_by_side()` на двух тестовых
PNG даёт файл нужной ширины (сумма ширин + отступ) с обоими исходными
изображениями видимыми по пикселям (не чёрный/пустой результат).

**Выгода.** Меньше ошибок «откатили одно — сломали другое», решение
принимается по разнице, а не по абсолютному состоянию.

## G. Журнал времени и итераций

**Проблема.** `GUIDE.md` документирует стоимость шагов один раз, вручную,
на одной машине. По каждому реальному проекту такой видимости нет —
нельзя ответить «сколько мы потратили» без пересмотра истории чата.

**Решение.** Новый модуль `lib/telemetry.py` без внешних зависимостей:

```python
def record(project_dir, stage, seconds, extra=None):
    """Добавляет строку в <project_dir>/run_log.jsonl: {ts, stage,
    seconds, extra}. Не решает, что медленно — просто пишет факт."""

def summary(project_dir):
    """Читает run_log.jsonl, возвращает суммарное время по стадиям
    и число повторов каждой стадии (возвраты на 3/4 видны как счётчик)."""
```

Вызывается из `make.py` вокруг каждой стадии (`time.time()` до/после,
один вызов `record`). Не требует изменений в существующих `lib/`-модулях.

**Критерий приёмки.** Smoke-чек: несколько вызовов `record()` +
`summary()` дают верную сумму и верное число повторов по стадии.

**Выгода.** Данные для реальной приоритизации следующих версий вместо
разовых прикидок — в частности, покажет, действительно ли фичи ускорения
рендера (вне рамок этого ТЗ) стоят вложения на конкретных проектах.

## H. Перцептивный дифф-гейт

**Проблема.** Возврат на шаг 3/4 может незаметно сдвинуть то, что уже было
утверждено раньше (материал, кадр) — сейчас это ловится только глазом,
если вообще ловится.

**Решение.** Новый модуль (рабочее имя `lib/diff.py`), без PIL/numpy
(проектное ограничение, подтверждённое опытом `silhouette.py`) — по образцу
`silhouette._rows()`, через `bpy.data.images.load()` + `.pixels`:

```python
def perceptual_diff(path_a, path_b, grid=(16, 16)):
    """Даунсемплинг обоих PNG до grid усреднением по ячейке (без внешних
    библиотек), затем максимальная и средняя разница по ячейкам.
    Дешёвый, грубый, но достаточный для гейта "что-то заметно сдвинулось"."""
```

Используется вместе с F: при наличии `<stage>.approved.png` — не только
показать сравнение рядом, но и посчитать `perceptual_diff`, и явно
предупредить, если разница выше грубого порога, на шаге, который не
должен был её менять.

**Критерий приёмки.** Smoke-чек: `perceptual_diff(x, x) == 0`;
`perceptual_diff` на существенно разных синтетических изображениях выше
условного порога.

**Выгода.** Регрессии видны числом на месте, а не постфактум при
финальном просмотре — дешевле всего поймать в момент, когда они возникли.
